# 正式数据版上线方案_2026-03-30

## 一、正式数据库接入方案

### 1. 推荐方案
当前项目建议继续沿用：

- `Next.js`
- `Prisma`
- `PostgreSQL`
- `Netlify`

正式数据版不建议重构架构，直接把“试运行的 fallback 架构”收口成“真实数据库优先、fallback 仅兜底”的正式运行模式即可。

### 2. 为什么 PostgreSQL 适合当前项目
当前项目的 Prisma Schema 已经明确使用：

- `provider = "postgresql"`

并且现有数据模型具备以下特点，和 PostgreSQL 很匹配：

1. 强结构化业务表较多  
包括：
- 客户
- 项目
- 应收
- 合同
- 风险记录
- 信用评分
- 催收任务
- 月报
- 完整账款档案

2. 既有结构化字段，也有 JSON 扩展字段  
例如：
- `extra_fields`
- `extra_summary`
- `sheet_data_json`
- `risk_summary`
- `receivable_summary`

PostgreSQL 对 JSON/JSONB、索引、事务支持都比较成熟，适合当前“结构化主数据 + 原始档案半结构化数据”的混合场景。

3. 适合 Netlify 外部连接  
Netlify 运行环境不能访问你电脑本地数据库，因此正式环境应使用可公网访问、支持 TLS 的托管 PostgreSQL。

推荐类型：
- Neon
- Supabase Postgres
- Railway Postgres
- 阿里云 / 腾讯云 / AWS RDS PostgreSQL

### 3. 正式环境建议
正式数据版建议采用：

- 一套正式 PostgreSQL 数据库
- Netlify 只作为 Web/Functions 运行环境
- Prisma 作为数据库访问层
- 所有关键页面和 API 真实数据库优先

### 4. 当前正式上线最小环境变量
当前项目真正硬依赖的环境变量是：

- `DATABASE_URL`
- `SITE_ACCESS_PASSWORD`

建议说明如下：

#### `DATABASE_URL`
- 用途：Next.js Runtime / Prisma 查询正式数据库
- 必填：是
- 适用：Build + Functions Runtime
- 正式上线是否必须：必须

#### `SITE_ACCESS_PASSWORD`
- 用途：试运行 / 正式内控访问密码
- 必填：是
- 适用：Functions Runtime
- 正式上线是否必须：建议保留

### 5. 建议的正式数据库连接原则
1. 使用可从 Netlify 访问的托管 PostgreSQL
2. 开启 TLS/SSL
3. 不要继续依赖本地电脑数据库
4. 正式环境必须有真实 `DATABASE_URL`
5. 正式环境下，关键页面不应再以 development/mock 数据作为主来源

## 二、当前 Prisma 结构审核

### 1. 正式上线需要的核心表
从 `prisma/schema.prisma` 看，正式数据版的核心表至少包括：

#### 主数据层
- `customers`
- `projects`
- `contracts`
- `receivables`

#### 完整账款档案层
- `customer_ledger_profiles`
- `customer_ledger_rows`

#### 风控层
- `risks`
- `credit_scores`

#### 跟进与管理层
- `collection_tasks`
- `monthly_reports`
- `system_logs`

#### 数据治理层
- `customer_merge_mappings`
- `import_logs`
- `import_errors`

### 2. 哪些表承载“完整账款档案”所需真实数据
完整客户档案 / 完整账款档案最核心依赖的是：

#### `customer_ledger_profiles`
承载：
- `sheet_name`
- `workbook_source`
- `project_name`
- `settlement_clause`
- `contract_unpaid_total`
- `uninvoiced_total`
- `extra_summary`
- `sheet_data_json`

这是完整 sheet 的“档案头 + 二维结构 + 汇总信息”。

#### `customer_ledger_rows`
承载：
- `statement_date`
- `quantity`
- `statement_amount`
- `contract_receivable`
- `received_date`
- `received_amount`
- `cumulative_receivable`
- `invoice_date`
- `invoice_quantity`
- `invoice_amount`
- `remark`
- `extra_fields`

这是完整 sheet 的“主明细行数据”。

### 3. 当前 fallback 依赖的数据与真实数据的差异
当前 fallback 主要来自：
- `lib/server/development-dataset.ts`
- `lib/mock-data.ts`

其特点是：

#### 能提供
- 客户
- 项目
- 应收
- 合同
- 风险
- 评分
- 催收列表

#### 不能完整等价替代
- 真实 `customer_ledger_profiles`
- 真实 `customer_ledger_rows`
- 真实导入日志
- 真实风险记录时间线
- 真实多 sheet 原始 Excel 结构

所以：
- fallback 适合试运行演示
- 不适合作为正式数据版的长期主数据来源

## 三、正式数据版上线实施清单

### 1. 建库
- 选择托管 PostgreSQL 服务
- 创建正式数据库实例
- 建立正式数据库账号
- 开启公网访问或允许 Netlify 访问
- 配置 SSL/TLS

### 2. Migration 执行
- 在本地或 CI 环境配置正式数据库连接
- 执行 Prisma migration
- 确认所有核心表创建成功

### 3. 本地真实数据导出
- 导出本地现有正式候选数据
- 优先导出：
  - 客户
  - 项目
  - 应收
  - 风险
  - 评分
  - 完整账款档案

### 4. 线上数据库导入
- 先导入结构化主数据
- 再导入档案数据
- 再导入风险/评分/任务类数据
- 导入后做抽样核对

### 5. Netlify 环境变量配置
- 配置 `DATABASE_URL`
- 配置 `SITE_ACCESS_PASSWORD`

### 6. 部署验证
- 构建成功
- 页面打开成功
- 关键 API 能查到正式数据库数据
- 客户详情页能展示真实完整档案
- 风控页面能基于正式数据返回风险结果

### 7. 回滚方案
- 保留试运行环境变量和历史构建版本
- 保留导入前数据库快照
- 必要时回滚到：
  - 旧数据库快照
  - 上一个 Netlify 发布版本

---

## 四、数据迁移方案

### 1. 迁移目标
把当前本地数据库 / 本地已导入数据迁到正式 PostgreSQL，形成可持续运行的正式数据底座。

### 2. 迁移分层

#### A. 结构迁移
对象：
- Prisma schema 对应所有核心表

方式：
- 执行 Prisma migration

#### B. 主数据迁移
对象：
- `customers`
- `projects`
- `contracts`
- `receivables`

方式：
- 直接从本地 PostgreSQL 导出导入
- 或通过 SQL / pg_dump 迁移

#### C. 档案 / 台账数据迁移
对象：
- `customer_ledger_profiles`
- `customer_ledger_rows`

方式：
- 作为重点迁移对象单独校验
- 必须保证 profile 和 rows 的关联完整

#### D. 风控与历史记录迁移
对象：
- `risks`
- `credit_scores`
- `collection_tasks`
- `monthly_reports`
- `customer_merge_mappings`
- `import_logs`
- `import_errors`

方式：
- 建议在主数据迁移完成后再导入

### 3. 建议执行顺序
1. 建正式库
2. 跑 migration
3. 导入客户 / 项目 / 合同 / 应收
4. 导入完整账款档案
5. 导入风险 / 评分 / 任务 / 导入日志
6. 验证客户详情页与风控页面
7. 再切 Netlify 指向正式库

### 4. 验证步骤
迁移后至少核对：
- 客户总数
- 项目总数
- 应收总数
- 风险记录总数
- 完整账款档案总 sheet 数
- 重点客户详情页是否能显示真实档案
- 风控总览页指标是否合理

## 五、仍依赖 development/mock fallback 的关键 API 检查

### 正式上线前必须改成“强制真实数据库优先”的关键 API
这些接口是正式数据版主链路，不应继续以 fallback 为主来源：

- `/api/customers`
- `/api/customers/ledger`
- `/api/customers/[id]/full-profile`
- `/api/customers/[id]/account-ledger-profile`
- `/api/customers/[id]/summary`
- `/api/customers/[id]/projects`
- `/api/risk/overview`
- `/api/risk/customers`
- `/api/risk/projects`
- `/api/dashboard/overview`
- `/api/contracts`
- `/api/receivables`
- `/api/risks`
- `/api/scores`
- `/api/collections`

这些接口当前虽然都有 fallback 兜底能力，但正式上线后建议口径是：
- 有数据库时必须以数据库为准
- 无数据库应返回明确错误或运维提示
而不是继续默默走展示用 fallback

### 可保留 fallback 作为兜底的接口
这类接口可以保留轻量 fallback，但不应影响主业务判断：

- `/api/health`
- `/api/auth/login`
- `/api/openclaw/export`

### 当前不建议纳入正式上线主链路的接口
- `/api/import/excel`

原因：
- 依赖文件上传、Python、导入脚本
- 更适合后台导入或运维导入，不建议作为 Netlify 正式环境在线主能力

## 六、下一步最先要做的 3 件事

### 1. 先确定正式 PostgreSQL 并拿到正式 `DATABASE_URL`
这是第一优先级。  
没有正式数据库，正式数据版上线无法成立。

### 2. 先完成本地真实数据库到正式数据库的迁移演练
至少做一轮：
- migration
- 数据导出
- 数据导入
- 客户详情页与风控页核验

### 3. 再把 Netlify 指向正式数据库并做上线回归
回归至少覆盖：
- `/login`
- `/customers`
- `/customers/[id]`
- `/risk`
- `/risk/customers`
- `/risk/projects`
