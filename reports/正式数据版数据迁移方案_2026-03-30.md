# 正式数据版数据迁移方案_2026-03-30

## 一、迁移目标
本次迁移的目标不是“把演示站上线”，而是把当前本地已经整理好的真实业务数据迁到正式 PostgreSQL，使系统从试运行模式切换为正式数据版运行模式。

迁移成功的标准是：
- 客户主数据完整
- 项目与应收关系完整
- 完整账款档案可正常显示
- 风控页面基于真实数据库返回结果

---

## 二、迁移范围

### 1. 结构迁移
需要迁移的是 Prisma Schema 对应的数据结构：
- `customers`
- `projects`
- `contracts`
- `receivables`
- `customer_ledger_profiles`
- `customer_ledger_rows`
- `risks`
- `credit_scores`
- `collection_tasks`
- `monthly_reports`
- `customer_merge_mappings`
- `import_logs`
- `import_errors`

### 2. 主数据迁移
主数据包括：
- 客户主体
- 项目主体
- 合同
- 应收账款

### 3. 档案 / 台账数据迁移
重点对象：
- `customer_ledger_profiles`
- `customer_ledger_rows`

这是“完整账款档案”能否在线上恢复真实展示的关键。

### 4. 风控相关数据迁移
包括：
- 风险记录
- 信用评分
- 催收任务
- 月报

---

## 三、迁移策略

### A. 结构迁移
推荐方式：
- 使用 Prisma migration 创建正式库结构

执行原则：
1. 正式库先空库建结构
2. 不建议直接手写表结构
3. 先确认 migration 成功，再导数据

### B. 主数据迁移
推荐方式：
- 从本地 PostgreSQL 导出，再导入正式 PostgreSQL

建议优先顺序：
1. `customers`
2. `projects`
3. `contracts`
4. `receivables`

原因：
- 这些表之间有主外键依赖
- 先主数据，后扩展数据，最稳

### C. 档案 / 台账数据迁移
推荐方式：
- 单独导出导入
- 迁移后做专项核验

建议顺序：
1. `customer_ledger_profiles`
2. `customer_ledger_rows`

必须核验：
- `profile.id` 与 `row.profile_id` 是否完整对应
- `sheet_data_json` 是否完整导入
- `extra_summary` 是否未丢失

### D. 风控与历史数据迁移
推荐顺序：
1. `risks`
2. `credit_scores`
3. `collection_tasks`
4. `monthly_reports`
5. `customer_merge_mappings`
6. `import_logs`
7. `import_errors`

---

## 四、建议执行顺序

### 第 1 步：准备正式库
- 创建正式 PostgreSQL
- 获取连接串
- 确认可从 Netlify 访问

### 第 2 步：结构迁移
- 配置正式 `DATABASE_URL`
- 执行 migration
- 确认所有核心表存在

### 第 3 步：主数据迁移
- 导出本地：
  - `customers`
  - `projects`
  - `contracts`
  - `receivables`
- 导入正式库

### 第 4 步：完整档案迁移
- 导出本地：
  - `customer_ledger_profiles`
  - `customer_ledger_rows`
- 导入正式库

### 第 5 步：风控与辅助数据迁移
- 导出导入：
  - `risks`
  - `credit_scores`
  - `collection_tasks`
  - `monthly_reports`
  - `customer_merge_mappings`

### 第 6 步：迁移后验证
至少验证：
- 客户总数
- 项目总数
- 应收总数
- 风险记录总数
- 完整账款档案页是否恢复真实内容
- 风控总览页是否正常

### 第 7 步：Netlify 指向正式库
- 配置正式环境变量
- 触发部署
- 做线上回归

---

## 五、验证步骤

### 1. 结构验证
确认正式库中存在这些关键表：
- `customers`
- `projects`
- `receivables`
- `customer_ledger_profiles`
- `customer_ledger_rows`
- `risks`

### 2. 数据量验证
建议对比：
- 客户数
- 项目数
- 应收条数
- 风险记录条数
- 档案 profile 数
- 档案 row 数

### 3. 页面验证
重点验：
- `/customers`
- `/customers/[id]`
- `/risk`
- `/risk/customers`
- `/risk/projects`

### 4. 样本验证
建议至少抽样：
- 云龙小学
- 96#地块
- 青水澜湾
- 已诉 / 待起诉项目
- 高金额高未收项目

---

## 六、回滚方案

### 1. 数据回滚
正式导入前先保留：
- 正式库导入前快照
- 本地库导出快照

### 2. 应用回滚
保留：
- 上一个 Netlify 成功部署版本
- 原试运行环境变量配置

### 3. 回滚原则
一旦出现以下问题，可回滚：
- 客户详情页完整档案大面积缺失
- 风控结果明显异常
- 主数据数量严重不一致
- 正式数据库性能或连通性不稳定

---

## 七、注意事项
1. 迁移时不要只迁主数据，必须迁完整档案数据
2. 正式环境不应继续依赖 development/mock 数据作为主来源
3. 在线 Excel 导入不建议作为正式数据版上线首批能力
4. 迁移完成后必须做页面级回归，而不只是 SQL 级核对

---

## 八、一句话建议
正式数据版上线最稳的路径不是重构，而是：
- 先建正式 PostgreSQL
- 再按“结构 -> 主数据 -> 档案 -> 风控数据”的顺序迁移
- 最后切 Netlify 并做回归验证
