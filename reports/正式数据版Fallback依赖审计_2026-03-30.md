# 正式数据版 Fallback 依赖审计_2026-03-30

## 一、审计目的
本次审计的目标是明确：
- 当前哪些关键 API 仍依赖 development/mock fallback
- 哪些正式上线前必须改成“真实数据库优先”
- 哪些可以保留轻量 fallback 作为兜底

---

## 二、当前 fallback 数据来源

当前项目的主要 fallback 来源包括：

### 1. development dataset
文件：
- `lib/server/development-dataset.ts`
- `data/imported/zhongcheng-development-dataset.json`

当前提供：
- `customers`
- `receivables`
- `contracts`
- `risks`
- `creditScores`
- `collections`

### 2. mock-data
文件：
- `lib/mock-data.ts`

当前主要作为：
- 早期演示数据
- OpenClaw mock 导出
- development dataset 缺项时的补位

### 3. 开发档案自动生成 fallback
文件：
- `lib/server/data-access.ts`

当前用途：
- 在无数据库场景下，为客户详情页生成 development fallback 的完整账款档案结构

## 三、关键 API 当前状态

### A. 正式上线前必须强制真实数据库优先

#### `/api/customers`
用途：
- 客户主体列表
- 客户管理页基础入口

当前状态：
- 有数据库时走真实数据库
- 无数据库时回退到 development dataset

正式上线建议：
- 必须以真实数据库为主
- fallback 只可作为故障兜底，不应成为常态

#### `/api/customers/ledger`
用途：
- 客户总账页
- 项目金额与风险聚合

当前状态：
- 有数据库时走真实数据
- 无数据库时可回退 development dataset

正式上线建议：
- 必须真实数据库优先

#### `/api/customers/[id]/full-profile`
用途：
- 客户详情页主体信息

当前状态：
- 有数据库时走真实数据
- 无数据库时回退 development dataset

正式上线建议：
- 必须真实数据库优先

#### `/api/customers/[id]/account-ledger-profile`
用途：
- 完整账款档案 / 原始 sheet 展示

当前状态：
- 有数据库时读 `customer_ledger_profiles` 与 `customer_ledger_rows`
- 无数据库时生成 development fallback 档案

正式上线建议：
- 必须以真实档案表为主
- fallback 仅保底，不应成为正式环境常态

#### `/api/customers/[id]/summary`
#### `/api/customers/[id]/projects`
用途：
- 客户详情辅助数据

正式上线建议：
- 真实数据库优先

#### `/api/risk/overview`
#### `/api/risk/customers`
#### `/api/risk/projects`

- 风险客户

当前状态：
- 依赖主数据 + 风险规则聚合
- 无数据库时仍可用 fallback 跑出结果

正式上线建议：
- 强制真实数据库优先
- fallback 仅作应急，不应作为正式口径

#### `/api/dashboard/overview`
#### `/api/contracts`
#### `/api/receivables`
#### `/api/risks`
#### `/api/scores`
#### `/api/collections`
正式上线建议：
- 同样应以真实数据库为准

### B. 可以保留 fallback 作为兜底的接口

#### `/api/auth/login`
当前状态：
- 走站点访问密码
- 不依赖数据库

建议：
- 可保留

#### `/api/health`
当前状态：
- 运行时健康检查

建议：
- 可保留轻量兜底

#### `/api/openclaw/export`
当前状态：
- mock 数据

建议：
- 可以继续保留为演示/占位接口
- 不影响第一版正式数据主链路

---

### C. 不建议纳入正式数据版首批上线主链路

#### `/api/import/excel`
原因：
- 依赖 Python、脚本、文件处理
- 更适合后台导入，不适合作为 Netlify 正式运行时主能力

## 四、当前 fallback 与真实数据的核心差异

### 1. 客户和项目层
fallback 可以提供：
- 基础客户信息
- 基础项目信息
- 应收金额
- 风险摘要

但正式数据库能提供：
- 更完整的主数据一致性
- merge 后的真实客户主体
- 更稳定的项目归属 / 项目状态

### 2. 完整账款档案层
fallback 现在可以“展示结构”
但真实数据库能提供：
- 真正导入的原始 sheet
- 真正的 sheetDataJson
- 真正的 customer_ledger_rows
- 多 sheet 对应关系

### 3. 风控记录层
fallback 可以算风险
但真实数据库才有：
- 风险记录时间线
- open/closed 状态
- 风险来源
- 后续跟踪闭环

---

## 五、正式数据版上线建议
结论非常明确：

### 正式上线前必须保证
1. `DATABASE_URL` 配置为正式 PostgreSQL
2. 关键业务接口以真实数据库优先
3. 完整账款档案必须来自：
   - `customer_ledger_profiles`
   - `customer_ledger_rows`

### 可以保留但不应依赖
1. development dataset
2. mock-data
3. 开发档案自动生成 fallback

它们可以作为：
- 本地开发兜底
- 演示环境兜底

但不应作为：
- 正式环境主数据来源

---

## 六、一句话结论
当前项目已经具备正式数据版上线的代码基础，但正式上线前必须完成一件关键事：

- **让主链路 API 从“可 fallback”切换为“真实数据库优先、fallback 仅兜底”**
